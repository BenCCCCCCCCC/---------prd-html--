## EXT-01｜Codex Harness 与自我审核循环

**新增：** 用简短 `AGENTS.md` 提供地图，详细规则分散在可索引文档；把架构、命名、状态边界、视觉禁区、测试与交付格式变成可检查的约束；要求 Codex 启动应用、操作流程、读取 DOM/日志、生成截图、依据审查结果修复，再统一回交。

**为什么：** 一次长提示并不能保证长期一致；真正降低人工审查成本的是稳定事实源、可观察输出和自动反馈循环。

**来源：** OpenAI, *Harness engineering: leveraging Codex in an agent-first world*, 2026-02-11。

**影响：** 只改变制作方式，不改变 PRD。

## EXT-02｜双层作品集叙事

**新增：**

- 90 秒快速扫描：角色、问题、证据边界、3 个关键决策、Demo 入口、当前验证状态。
- 8 分钟深读：用户分层、取舍、状态/规则、AI 边界、实验与反思。
- 所有结论标记为“事实 / 推断 / 假设 / 模拟”，没有真实数据时显示“待验证”，不使用虚构增长数字。

**为什么：** 公开作品集的直接用户是招聘者和用人经理，不是课程老师。先帮助其判断“是否值得继续看”，再提供足够深度。

**来源：** Nielsen Norman Group, *UX Hiring: Insights from a Design Recruiter*, 2026-01-16；NN/g 关于作品集筛选与面试支持的既有指导。

## EXT-03｜四类产品风险

**新增：**

- Value：用户是否真的需要主动控制，而不是只口头说需要。
- Usability：能否理解“仅本次 / 临时收听 / 少推 / 黑名单”。
- Feasibility：推荐、画像、事件、撤销与刷新分阶段实现是否可行。
- Viability：是否伤害总收听、多样性、内容分发与运营策略。

**来源：** Silicon Valley Product Group, *The Four Big Risks*（基础框架）。

**影响：** 补充作品集思考，不增加新功能。

## EXT-04｜Spotify / Apple 最新行业对照与 R07 重新定位

**新增：**

- Spotify 已在开放该 Beta 的市场提供 Taste Profile；符合条件的 Premium 移动端用户可以用文字描述希望调整的推荐方向。官方同时说明它不能替用户执行 follow，也不能建立 always/never 规则。
- Spotify 可按播放列表/曲目排除 Taste Profile，并明确同一歌曲从其他上下文播放时仍可能被计入。
- Apple Music 可关闭 Use Listening History，使播放习惯不影响后续推荐与 Replay；官方提供家长临时让孩子听歌的 Focus 示例。

**由此调整叙事：** R07 不再宣传“自然语言调推荐是行业首创”，改为强调：

> 短期会话优先、结构化候选、影响范围预览、手动修正、最终确认、AI 无直接画像权限、提交后可撤销。

**来源：** Spotify Support, *Taste Profile*；*Exclude a playlist or track from your taste profile*；Apple Support, *Rate and personalise music*，于 2026-09-05 复核。

**取舍：** 创新叙事更克制，但可信度和行业敏感度更高。推荐批准。

## EXT-05｜AI 体验：先设预期，再允许修正

**新增：**

- 名称固定为“AI 建议草稿（实验）”，旁边注明“本地规则模拟”。
- 首次展示支持示例和暂不支持范围。
- 结果展示“识别到什么 / 未识别什么 / 会改哪些字段 / 影响多久”。
- 用户可以直接编辑结构化候选或回到手动设置，无需整句重写。
- 提交前说明后果，提交后显示具体回执与撤销。
- 使用 `已识别 / 需确认 / 暂不支持 / 出错`，不展示未经校准的 0.89 等置信度。

**来源：** Microsoft HAX Guidelines 1、2、9、11、15、16。

## EXT-06｜AI 契约与 Eval

**新增：**

- `specs/intent.schema.json` 作为结构唯一事实源，生成 TypeScript 类型并检查漂移。
- 运行时依次做输入、Schema、字典、冲突、权限校验，再做语义预览。
- 结构合法不等于语义正确；覆盖正常、边界、歧义、无关、否定、越权和对抗输入。
- 本地规则解析器是公开 Beta 默认实现；真实模型适配器保持关闭。
- 未来若接真实模型，密钥只能在服务端；接入需另行授权、预算和停用开关。

**来源：** OpenAI Structured Outputs；OpenAI Evals 公开材料；OpenAI API Key Safety（2026-09 更新）。

## EXT-07｜实验健康门槛

**新增：** 在读取核心效果前先检查：

1. 曝光、分组、事件、时间戳与版本字段完整。
2. 随机化单位和分组一致。
3. 是否存在 Sample Ratio Mismatch；有 SRM 时不读取效果结论。
4. A/A 或最小数据链路通过。
5. 用户分层只用实验前特征，避免用功能后的行为造成自选择偏差。
6. 数据质量、OEC、诊断和 Guardrail 同时存在。
7. 每个灰度 ring 都有人群、时长、核心指标和 pass/hold/rollback 标准。

**来源：** Microsoft Experimentation Platform 关于数据质量、SRM 与 A/A 的官方资料。

**注意：** 不照搬“每组十万”或固定 p 值；样本量和阈值必须由真实基线、方差、MDE 与公司标准确定。

## EXT-08｜无障碍与视觉 QA

**新增：**

- Bottom Sheet 使用原生 `<dialog>` 或等效可访问实现；打开时焦点进入，Tab 不离开，Esc 关闭，关闭后焦点返回触发器。
- 44×44 是本项目更严格的触控目标，不误称为 WCAG 的统一最低值。
- 任何滑动/拖动都有可点击替代。
- Playwright + axe 只声明“自动检查未发现可检测问题”，不能代替键盘、缩放和读屏检查。
- 视觉快照在同一 OS、浏览器、字体和配置生成。

**来源：** W3C WAI-ARIA Dialog Pattern、WCAG 2.2、Playwright、MDN `<dialog>`。

## EXT-09｜性能与部署准备

**新增：**

- 本地 Beta 记录实验室性能，参考 LCP ≤2.5s、INP ≤200ms、CLS ≤0.1。
- 这些阈值面向真实用户 field 数据的判断；一次本地测量不能声称达到真实 Core Web Vitals。
- 无远程字体、无自动视频、图片固定尺寸、核心流程不依赖外网。
- 为静态部署保留路径配置，但本批不公开部署。

**来源：** web.dev Core Web Vitals；Vite Static Deploy。

## EXT-10｜网易云 Melo/Muse Mix 生产研究

**最新发现：** 2026 年 7 月公开的论文 *Melo: A Production LLM-Powered Music Recommendation Agent* 描述了已部署在网易云音乐的自然语言音乐推荐 Agent，作为 Muse Mix 的底层引擎。论文强调：从 Demo 到生产的关键不是只换更强模型，而是固定步骤、实体 grounding、失败检查和可控重试。

**对本项目的新增：**

- R07 明确不是“网易云首个自然语言推荐”，也不与 Muse Mix 争夺完整歌单生成定位。
- 本项目差异化收窄为：把一句话转换成**可编辑的推荐控制设置**，尤其解释“影响多久、是否进入长期画像”，最终仍由用户确认。
- 本地 Beta 使用固定链路，不做自由循环 Agent。
- 音乐人、歌曲和标签必须在合成曲库/字典中 grounding；无法确认时澄清或拒绝。
- 约束过紧导致无结果时，不能静默丢掉用户核心条件；若建议放宽，必须显示具体变化并再次确认。

**来源：** Wang et al., *Melo: A Production LLM-Powered Music Recommendation Agent*, arXiv/RecSys 2026，2026-07-26。

**边界：** 论文披露的产品指标、离线消融和延迟是外部研究结果，不能写成本项目结果；它也不证明 R03/R04 必然有用户价值。

## EXT-11｜网易云音乐 H1 2026 业务背景

**新增：** 在深读层或来源说明中简短提到：网易 2026 年上半年公开结果显示，网易云音乐收入约 40 亿元、同比增长 3.4%；公司公开表述继续改进个性化推荐与产品功能，并报告 DAU/MAU 仍高于 30%。

**为什么只放深读层：** 这能说明项目针对的是一个成熟、高活跃的在线音乐业务，控制类改动需要谨慎看总体验和商业可持续性；但这些数据不能证明用户需要本方案，也不能用来推导上线收益。

**来源：** NetEase 2026 Q2/Interim Results；NetEase Cloud Music H1 2026 Results announcement，2026-08。

**推荐：** 批准，但不在 Hero 放收入数字，不做“平台增长所以本项目重要”的虚假因果。

## 本轮由助手代为回答的问题

| 反问 | 推荐答案 |
|---|---|
| 公开首版是否接真实 AI？ | 不接。先证明规则、权限、可修正与 Eval；真实模型另开受控适配器。 |
| R07 是否放在作品集 Hero？ | 不放。Hero 讲推荐控制问题，R07 在核心链路后作为 AI 实验。 |
| Melo 已存在后，R07 是否还值得做？ | 值得，但定位为“控制层助手”，不是完整歌单生成 Agent；核心竞争点是范围、权限、预览与撤销。 |
| 是否继续把 HTML 做成网易云高仿？ | 不做高仿。保留播放器与暗色控制层识别，外层用独立案例叙事并明确非官方。 |
| 是否加入 Spotify 为新竞品？ | 加入“2026 行业复核”，不篡改当时课程作业的竞品时间线。 |
| 是否展示成果数字？ | 只展示实际执行的规格/代码/可用性测试结果；当前不写业务增长。 |
| 是否现在公开部署？ | 不。先完成本地 Beta、视觉与内容审查，再单独发布审查。 |
| 是否使用真实歌曲、封面和账号？ | 不。全部使用虚构曲库和自制几何封面。 |
| 是否让 Codex 自主改产品规则？ | 不。实现细节可自主；范围、权限、生命周期变更必须集中升级。 |
| 是否把公司 H1 数据放首屏？ | 不。只在深读层作业务背景，避免抢走用户问题和设计决策。 |

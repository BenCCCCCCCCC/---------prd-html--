# 外部行业研究增补（Batch 2）

版本：0.3 / 2026-09-05
状态：approved_for_local_beta（EXT-01 至 EXT-11 已批准；仅授权本地 Beta）

本文件只记录 Batch 1 以后新增的外部研究。课程转写、原 PRD 与 Batch 1 规格仍是项目主依据；外部研究不能被写成老师原话、用户调研结论、网易内部规则或本项目效果。

## 1. 实施方法：Agent-first Harness

### 采用

- `AGENTS.md` 只做地图，不把所有细节塞成一份巨大说明。
- repo 内文档、schema、fixtures、tokens、测试和 handoff 共同构成事实源。
- 架构、数据边界、状态权限、视觉禁区和交付格式尽量变成机械检查。
- Codex 必须能直接看见 UI、DOM、日志、测试和截图，并在回交前完成“实现 → 操作 → 审查 → 修复 → 重跑”。
- 只在需要产品判断或真实外部权限时升级；普通实现问题自行处理并记录假设。

### 不采用

- 不根据 OpenAI 个案宣称本项目能节省 10 倍时间。
- 不允许 Agent 自动公开、付费、调用真实账号或修改产品主语义。

## 2. 作品集：招聘者优先的双层阅读

### 快速层（目标约 90 秒）

1. 我的角色与项目状态。
2. 问题：短期意图和长期画像混在一起，用户难以纠偏。
3. 证据边界：课程研究、公开反馈、竞品复核；无真实问卷原始数据。
4. 三个关键决策：统一控制、临时隔离、AI 只提建议。
5. 可交互 Demo 入口。
6. 当前结果：完成了什么、尚未验证什么。

### 深读层（目标约 8 分钟）

用户分层 → 需求推导 → 竞品/行业复核 → 规则/状态 → 多角色流程 → AI 契约 → 指标/实验 → 风险/反思。

### 证据标签

- FACT：官方产品或已提供材料能直接支持。
- INFERENCE：由多个事实推导，明确标注推断。
- HYPOTHESIS：等待真实研究/实验。
- SIMULATION：只用于原型的参数、曲库、埋点或排序。

## 3. 产品分析：四类风险

| 风险 | 当前证据 | HTML 能验证什么 | 仍不能证明什么 |
|---|---|---|---|
| Value | 公开反馈、课程分析与行业相似控制 | 测试者是否理解、是否愿意完成任务 | 市场渗透率或真实留存提升 |
| Usability | Figma与老师反馈 | 入口、范围、撤销、少推/黑名单理解 | 大规模真实用户行为 |
| Feasibility | 规则、状态与依赖规格 | 前端状态、幂等、旧响应、降级可执行 | 网易内部推荐服务成本与工期 |
| Viability | Guardrail与投入产出假设 | 是否明确监控多样性和总体验 | 真实商业收益与内容生态影响 |

## 4. 2026 产品与行业复核

### Spotify Taste Profile Beta

在已经开放该 Beta 的市场，符合条件的 Premium 移动端用户可以查看 Spotify 如何理解其品味，并用文字描述希望调整的方向；官方说明该 Beta 不能替用户执行 follow，也不能直接建立 always/never 规则。由此，R07 不以“首次自然语言调推荐”为卖点，而以权限、范围、结构化预览和可修正性建立差异。

### Spotify 排除 Taste Profile

Spotify 支持排除播放列表或曲目，使过去和未来的相关播放对品味摘要与推荐影响更小；同一歌曲若从其他上下文播放仍可能计入。此限定支持把“对象控制”和“会话隔离”分开建模。

### Apple Listening History

Apple Music 可关闭 Use Listening History，使听歌习惯不用于新推荐和 Replay；官方还提供家长临时让孩子听歌的 Focus 场景。这为临时收听提供行业可行性证据，但不证明网易云用户一定需要相同交互。

### NetEase Melo / Muse Mix

2026 年公开的 Melo 论文描述了部署在网易云音乐的自然语言音乐推荐 Agent。其生产设计使用确定性五节点状态图、结构化输入输出、实体 grounding、结果检查和受限反思重试。论文最重要的可迁移认识是：生产体验的关键不仅是模型能力，还包括在错误影响用户之前发现、定位和恢复。

本项目不复制 Melo，也不宣称比它更先进。R07 定位为“推荐控制层助手”：把一句话转成可编辑设置，让用户确认范围、长期影响和任何放宽条件。它不承担完整歌单生成。

### NetEase Cloud Music H1 2026

公开公司信息可用于说明业务背景：平台继续强调个性化推荐、产品功能、用户参与和会员业务。但收入、DAU/MAU 或外部论文指标都不能成为本方案用户价值或效果的证据。

## 5. Human-AI Interaction

| 原则 | 本项目实现 |
|---|---|
| 明确系统能做什么 | 展示支持示例、200 字上限、有限标签和实体上下文。 |
| 明确可能出错 | 不显示假精度；使用“需确认/暂不支持”，保留手动入口。 |
| 高效纠正 | 直接修改结构化候选，而不是重写整句。 |
| 解释原因 | 展示输入片段到字段的映射与未识别片段。 |
| 细粒度反馈 | 对歌曲、音乐人、风格、范围分别确认。 |
| 说明后果 | 提交前显示影响范围；提交后显示保存/刷新结果和撤销。 |
| 高效关闭 | AI 实验可折叠、跳过或回到手动，不阻断核心任务。 |

## 6. AI 契约与评估

- JSON Schema 约束输出形状，不保证语义正确。
- `unsupported` 与 `needs_clarification` 是正常产品结果。
- 测试覆盖典型、边界、歧义、否定、无关、未知、越权和注入输入。
- 先做确定性校验，再做人类可理解的语义预览。
- 音乐人、歌曲、标签必须在合成目录/字典中 grounding。
- 无结果或约束过紧时，不静默丢弃核心条件；建议放宽时显示具体 diff 并确认。
- 评估资产留在仓库，结果绑定版本；失败案例进入回归集。
- 公开首版不依赖真实模型，也不在浏览器保存供应商密钥。

## 7. 实验可信度

新增实验前置 Gate：

1. Assignment 与 exposure 可追踪。
2. 关键字段完整、格式有效、时间可解释。
3. SRM 通过；失败时停止读效果。
4. A/A 或最小链路检查通过。
5. 分层字段来自实验前，避免处理后自选择偏差。
6. 数据质量、OEC、诊断和 Guardrail 同时存在。
7. 每个 ring 有预设人群、时长和 pass/hold/rollback。

## 8. Web 质量

- 使用原生 `<dialog>` 或等价实现；验证焦点、背景 inert、Esc 和焦点恢复。
- 所有拖动/滑动都有按钮替代。
- 关键触控区 ≥44×44（项目目标），不误称为 WCAG 的统一最低要求。
- Playwright + axe 只覆盖自动可检测问题；还需键盘、200% 缩放、320px、软键盘和读屏语义检查。
- 视觉快照在相同环境生成和比较。
- Lighthouse 使用实验室预算；只有发布后有足够 field 数据才能判断真实 Core Web Vitals。
